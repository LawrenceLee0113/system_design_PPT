Research Lens

SDLC 是把「想法」穩定變成「系統」的管理方法

為什麼需要階段？

系統開發牽涉業務目標、使用者流程、資料、程式、測試、導入與後續支援。五階段模型把不確定性拆小，讓團隊每一步都有明確產出。

五階段版本 規劃、分析、設計、實作、維護

LibreTexts 將 SDLC 定義為這五個階段的流程模型。

可調整性 不同組織可拆分或合併階段

例如有些團隊會把測試與部署拆成獨立階段，但核心邏輯仍是循序降低風險。

貫穿案例

一家餐飲品牌要開發線上訂餐系統，支援顧客下單、門市接單、庫存扣減、付款與訂單查詢。

01

Planning

規劃：先判斷問題值不值得被系統化

規劃階段會確認專案目標、範圍、預算、時程、利害關係人與可行性。它回答的不是「畫面長怎樣」，而是「為什麼現在要做」。

案例任務

評估線上訂餐是否能降低電話尖峰、減少漏單，並提高會員回購。

階段產出

專案章程、初步範圍、成本效益估算、風險清單、Go / No-Go 決策。

30%預估電話量下降
8 週MVP 時程
3 門市首波試點
02

Analysis

分析：把「大家覺得」變成可驗收需求

分析階段會訪談使用者與業務單位，理解現行流程、痛點、資料需求、權限與例外狀況。此時通常還不寫程式。

案例任務

訪談顧客、店員、店長與客服，整理下單、改單、缺貨、退款的實際流程。

階段產出

需求規格書、使用者故事、資料欄位、驗收條件、流程例外清單。

顧客選餐
門市確認
付款通知
備餐完成
03

Design

設計：把需求轉成工程團隊可建造的藍圖

設計階段會決定系統架構、資料庫、介面、API、權限、報表與整合方式。好的設計會讓後續實作少猜測、少返工。

案例任務

設計訂單服務、菜單服務、付款串接、門市後台與會員資料流。

階段產出

系統設計文件、ERD、API 規格、Wireframe、權限矩陣、測試策略草案。

Web App
Order API
Menu DB
Payment
Store POS
04

Implementation

實作：把設計文件變成可測試、可導入的系統

實作階段包含寫程式、整合元件、測試、資料轉換、使用者訓練與上線準備。許多模型會把測試或部署拆出來，但五階段版本常放在實作內處理。

案例任務

完成下單流程、付款回呼、門市接單頁，並進行單元測試、整合測試與使用者驗收。

階段產出

可運行系統、測試報告、訓練文件、資料移轉腳本、上線檢查表。

POST /orders
validateCart()
reserveInventory()
createPayment()
notifyStore()
05

Maintenance

維護：讓系統在真實世界裡繼續健康運作

維護階段會處理錯誤回報、修補、備份、效能、安全更新與新功能優先順序。它也會把營運回饋帶回下一輪規劃。

案例任務

上線後監控付款失敗率、熱門時段效能、門市缺貨同步與客服回報。

階段產出

版本更新、問題單、SLA 報表、備份紀錄、下一版需求池。

System Health 99.92% uptime 付款錯誤率 0.4% 平均回應 180ms

同一個訂餐系統，在五階段中逐步變清楚

階段核心問題訂餐系統例子
規劃值得做嗎？估算降低尖峰電話與漏單的效益
分析要做什麼？整理下單、改單、退款、缺貨需求
設計怎麼做？規劃 API、資料庫、付款與門市後台
實作做出來了嗎？開發、測試、訓練並導入試點門市
維護能長期運作嗎？監控、修補、備份並累積下一版需求

一句話帶走

SDLC 的價值不是把流程變慢，而是讓團隊在每個關鍵決策點都能看見風險、產出與下一步。
