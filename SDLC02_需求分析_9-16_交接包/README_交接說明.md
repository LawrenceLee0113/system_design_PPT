# SDLC 02 系統需求分析 9-16 頁交接說明

這個資料夾整理第 9-16 頁「系統需求分析」段落，給共同編輯簡報的同學對照使用。

## 資料夾內容

- `README_交接說明.md`：本交接說明與每頁內容摘要。
- `preview/`：第 9-16 頁目前畫面的 PNG 預覽。
- `source/`：目前與這段投影片相關的來源檔副本。
  - `deck-data.js`：第 9-16 頁主要內容資料。
  - `deck.js`：新增或調整的頁面 renderer。
  - `deck-base.css`：第 9-16 頁相關排版樣式。
  - `deck-structure.test.mjs`：頁序與內容檢查測試。

## 整體主軸

這 8 頁要呈現一條清楚的需求分析邏輯：

```text
PM 規劃與使用者痛點
↓
系統角色與 Use Case
↓
使用者主要流程
↓
功能需求
↓
非功能需求
↓
系統需求書
↓
交給系統設計
```

重點不是只列功能，而是讓老師看懂「PM 規劃 → 使用者痛點 → 系統需求 → 系統需求書 → 系統設計」的轉換過程。

## 第 9 頁：系統需求分析

目標：說明系統分析師段落承接 PM 系統規劃，並將規劃內容轉成需求規格。

版型：三欄流程卡片。

內容：

- PM 系統規劃：專題背景、使用者痛點、服務定位、系統範圍、專案目標。
- 系統需求分析：確認主要使用者、整理 Use Case、分析主要流程、定義功能需求、定義非功能需求、建立驗收條件。
- 系統需求書：角色與權限、Use Case、流程規格、功能需求、非功能需求、資料需求、驗收條件。

底部句：

> PM 已經完成為什麼做、要解決什麼問題、系統範圍在哪裡；接下來系統分析師要把這些內容轉換成需求規格。

預覽：`preview/sdlc02-page-9.png`

## 第 10 頁：需求來源整理：痛點到系統需求

目標：說明需求不是憑空列出，而是從 PM 與使用者痛點推導而來。

版型：三欄對照表，第三欄「後續功能方向」高亮。

欄位：

- 使用者痛點
- 對應系統需求
- 後續功能方向

痛點包含：

- 3D 列印機購置成本高
- 不會操作 3D 列印機
- 價格與等待時間不清楚
- 取件不方便
- 不知道模型能不能印
- 模型內容可能有風險
- 不知道訂單進度
- 列印失敗不知道怎麼處理

底部重點句已放在 note：

> 系統需求分析的目標，是把使用者的問題轉換成系統必須提供的功能與限制條件。

預覽：`preview/sdlc02-page-10.png`

## 第 11 頁：Use Case 圖與角色互動

目標：呈現系統角色、各角色可操作功能，以及外部系統互動。

版型：正式 Use Case 圖風格。

左側角色：

- 顧客
- 門市人員
- 客服人員
- 管理員

中間系統邊界：

- 顧客相關：註冊 / 登入、上傳 3D 模型、查看估價、建立訂單、付款、查詢訂單、取件。
- 門市人員相關：查看待列印訂單、更新列印狀態、確認取件。
- 客服人員相關：處理列印失敗、處理退款、回覆客訴。
- 管理員相關：管理門市、管理設備、管理材料、管理價格規則、管理審核規範。

右側外部系統：

- 金流系統：付款確認、退款處理。
- 通知系統：付款 / 完成 / 異常 / 逾期通知。

權限邊界：

> 顧客只能查看自己的訂單；門市人員只能處理門市列印與取件狀態；客服人員處理異常與退款；管理員才能修改門市、設備、材料與價格規則。

預覽：`preview/sdlc02-page-11.png`

## 第 12 頁：使用者情境與主要流程

目標：說明正常情況下，顧客從上傳模型到門市取件的完整流程與角色分工。

版型：四泳道流程圖。

泳道：

- 顧客：註冊 / 登入、上傳 3D 模型、選擇材質與品質、選擇取件門市、付款、查詢狀態、到門市取件。
- 系統：驗證登入、檢查模型、自動估價、建立訂單、更新訂單狀態、發送通知。
- 金流系統：接收付款請求、確認付款結果、回傳付款成功或失敗。
- 門市人員：接收列印訂單、執行列印、更新列印狀態、確認顧客取件。

情境文字：

> 小明是設計科學生，需要列印一個小型模型。他透過系統上傳模型，選擇 PLA 材質與附近門市，系統完成檢查與估價後建立訂單。付款完成後，門市接收任務並列印，完成後系統通知小明取件。

底部句：

> 本頁為正常下單流程；付款失敗、模型不合格、列印失敗與逾期未取會進入異常流程。

預覽：`preview/sdlc02-page-12.png`

## 第 13 頁：功能需求分析

目標：整理系統必須提供哪些功能，並說明功能對應到哪些使用者需求。

版型：功能模組卡片。

功能模組：

1. 使用者管理
2. 模型上傳與檢查
3. 材料與品質選擇
4. 智慧估價
5. 門市選擇
6. 訂單管理
7. 付款與退款管理
8. 門市端管理
9. 通知系統
10. 後台與審核機制

底部句：

> 功能需求由痛點、Use Case 與主要流程推導而來，是後續模組設計與 API 規劃的依據。

預覽：`preview/sdlc02-page-13.png`

## 第 14 頁：非功能需求分析

目標：說明系統除了功能外，還需要安全、效能、可用、可靠、擴充、維護、追蹤與風險控管等品質要求。

版型：對照表，第三欄「對系統設計的影響」高亮。

非功能需求：

- 安全性
- 效能
- 可用性
- 可靠性
- 擴充性
- 可維護性
- 可追蹤性
- 合規與風險控管

底部重點句已放在 note：

> 非功能需求不是系統要做什麼功能，而是系統要做到什麼品質，會影響後續架構、權限、安全、資料表與異常處理設計。

預覽：`preview/sdlc02-page-14.png`

## 第 15 頁：系統需求書交付內容

目標：收斂需求分析成果，說明系統分析師最後交付的系統需求書如何成為後續設計依據。

版型：交付清單表格。

項目：

- 角色分析
- Use Case
- 主要流程
- 功能需求
- 非功能需求
- 資料需求
- 驗收條件

底部重點句已放在 note：

> 系統需求書的目的，是把 PM 的規劃與使用者痛點，轉換成後續系統設計可以依據的規格文件。

預覽：`preview/sdlc02-page-15.png`

## 第 16 頁：從需求分析接續系統設計

目標：銜接下一段系統設計，說明需求分析結果會如何轉成架構、資料表、模組、介面與狀態機。

版型：左右對照箭頭圖。

對應關係：

- 顧客需要上傳模型 → 顧客端 Web / App、模型上傳介面、File Storage
- 系統需要檢查模型 → 模型檢查模組
- 系統需要自動估價 → 智慧估價模組、PriceRule 資料表
- 使用者需要付款 → 金流服務、Payment 資料表
- 門市需要接收列印任務 → 門市端 / 後台、列印排程模組
- 使用者需要追蹤狀態 → 訂單管理模組、OrderStatusLog
- 列印完成要通知 → 通知服務、Notification 資料表
- 列印失敗要處理 → 異常流程、Refund、客服處理
- 高風險模型要審核 → Review 資料表、審核流程
- 系統未來要擴充 → 模組化架構、可維護後台

底部句：

> 後續系統設計會依照需求分析結果，進一步規劃系統架構、資料表關聯、模組輸入輸出、介面流程與訂單狀態機。

預覽：`preview/sdlc02-page-16.png`
